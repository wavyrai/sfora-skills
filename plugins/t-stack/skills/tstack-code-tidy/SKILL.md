# Tidy your diff before you commit

Writing code leaves residue: a log line from debugging, a helper you stopped calling, a check you added while unsure, a variable named in a different style from the rest of the file. None of it changes what the code does, and all of it makes the diff longer and the reviewer slower. This pass reads the diff as the reviewer will and removes what the change doesn't need. It never changes behaviour; if a removal would, it stays.

## Steps

1. **See the whole diff,** committed and uncommitted, against the branch's base:

   ```bash
   git status
   git diff <base>
   ```

2. **Go through it hunk by hunk** and mark what the change doesn't need (the full list is in `references/checklist.md`):
   - debug output: `console.log`, prints, temporary timers, dumped objects;
   - dead code: functions, exports, branches and parameters nothing reaches;
   - commented-out code;
   - defensive checks for states the types or the caller already rule out;
   - wrappers with one caller that only forward to another function;
   - stray files: scratch scripts, notes, snapshots nobody uses, local config;
   - names, imports and formatting that differ from the file's own style.
3. **Prove each mark before you remove it.** Search for callers of anything you delete, including dynamic uses (string keys, routes, re-exports, tests). Check that a "needless" check really is: the type rules it out, or the only caller already guarantees it. If you can't prove it, leave it and note it.
4. **Remove,** one kind at a time, so each edit is easy to check. Inline a one-caller wrapper into its caller; don't move its body somewhere new.
5. **Prove behaviour held.** Run the type check, the linter on the changed files and the project's tests. Compare the result with the run before the tidy: the same tests pass. A test that changed outcome means a removal changed behaviour. Put it back.
6. **Read the diff once more** against the base. It should be smaller, and every line left should belong to the change.

## Guardrails

- Behaviour stays the same. Not "probably the same": the tests pass as before, and you can say why each removal is safe.
- Only what this diff added. Code the diff didn't touch is out of scope, even when it's messy. File a card for it instead (`sfora-board`).
- A check at a boundary (user input, network, files, environment) is not needless. Validation at the edge stays.
- Follow the file's style, not your favourite. If the file uses `snake_case` keys, the new key does too.
- Don't reformat lines the change didn't touch. A noisy diff hides the real change from the reviewer.
- Generated files are regenerated by their script, never tidied by hand.
- Do this before `tstack-handoff`, and before the reviewer sees the diff, not after.

## Report

What you removed, by kind, with a count. What you kept that looked removable, and why. The test and type-check results before and after.
