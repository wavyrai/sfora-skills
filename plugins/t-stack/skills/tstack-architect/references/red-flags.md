# Red flags in a design

Check every candidate shape against this list before you pick one. Any hit sends the shape back for rework, or out.

## A thin module

The module has a big public interface and hides little behind it. Callers have to call three methods in the right order to do one thing, or pass options that name its internal stages. Learning the interface doesn't save them from learning the implementation.

A deep module is the opposite: a small interface with real work behind it. Don't confuse that with a deep call chain, which spreads one idea over many files.

## A decision that leaks

Two modules depend on the same internal choice: a storage format, a wire type, a policy. Changing it means editing both. Parse wire data into your own types at the edge and keep the wire type private.

## Modules cut by time

Separate "load", "check", "transform" and "save" modules often each re-learn the same shape and its rules. Group code by what it knows, not by when it runs.

## A method that only forwards

A method only forwards its parameters, unchanged, to a second method whose signature matches its own. The reader gets one more hop and no hidden detail in return. Remove it, unless it adds a rule, an adaptation or a real boundary.

## State with two writers

Two modules write the same state, or each keeps a copy. An agent edits one writer and can't see the other, and the rules drift apart. Give the state one owner; the others read it or ask the owner.

The t-stack learnt the same lesson at team scale: teammates work on separate files, and generated files are regenerated by their script, never merged by hand.

## Two ways to do one thing

The design offers two routes to the same result. Agents copy whichever they see first, so both keep gaining callers. Keep one, move the callers, delete the other in the same change.

## Internals you can import

A caller can reach a module's internals. Someone will, because it compiles, and then the internals are part of the interface. Make an outside import fail the build.

## A list kept in sync by hand

The same items are listed in two places, and adding one means editing both. Keep one list and derive the rest. If a list can't be derived, add a test that fails when they disagree, the way `packet.test.ts` fails when a skill folder isn't in the approved list.
